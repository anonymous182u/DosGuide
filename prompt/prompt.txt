1. Regex Backtracking (CWE-1333)
Allowed only if the target uses java.util.regex.
REQUIRED instrumentation depth (one or more):
	•	Instrument java.util.regex.Pattern / Matcher internals (via Java agent / bytecode instrumentation):
	•	Backtracking step count
	•	State transitions in the regex VM
	•	Visits to Pattern$Node.match(...)
	•	OR instrument catastrophic backtracking indicators:
	•	Count of recursive/iterative node evaluations
	•	Growth rate of backtracking states
Explicitly DISALLOWED:
	•	Counting how many times matches() / find() is called
	•	Timing only at the call site without internal step counters
Signal must approximate: "How many regex VM steps / backtracking states were explored for this input?"
2. Parsing Depth / Recursion (Parser DoS)
Applies to recursive descent or tree-building parsers.
REQUIRED instrumentation depth:
	•	Instrument parser entrypoints and recursive productions:
	•	Current and maximum recursion depth
	•	Number of AST / parse nodes created
	•	Total nodes visited during parse
	•	Prefer instrumentation inside parsing functions, not at the API boundary.
Explicitly DISALLOWED:
	•	Only measuring total parse time
	•	Only counting top-level parse invocations
Signal must approximate: "How deep and wide did the parser expand for this input?"
3. Decompression / Zip Bomb (CWE-409 / CWE-400)
Applies to ZIP, GZIP, Deflate, Brotli, etc.
REQUIRED instrumentation depth:
	•	Instrument Inflater / decoder internals:
	•	Total decompressed bytes emitted
	•	Expansion ratio (output bytes / input bytes)
	•	Decoder loop iterations
	•	Prefer counters inside Inflater.inflate(...) or equivalent.
Explicitly DISALLOWED:
	•	File size checks only
	•	Timing without output-size measurement
Signal must approximate: "How much output did the decoder produce relative to the input?"
4. JSON / XML Bombs
Applies to streaming or DOM parsers.
REQUIRED instrumentation depth:
	•	Instrument tokenizer / parser internals to record:
	•	Token count
	•	Element/object/array nesting depth
	•	Total nodes/elements created
	•	Instrument where tokens or nodes are created, not just when parsing starts/ends.
Explicitly DISALLOWED:
	•	Counting top-level parse calls
	•	Only measuring wall-clock parse time
Signal must approximate: "How many structural elements and how deep did the document expand?"
5. Hash Collision DoS
Applies to hash-based data structures (e.g. HashMap, HashSet).
REQUIRED instrumentation depth:
	•	Instrument hash table internals:
	•	Bucket depth
	•	Number of key comparisons
	•	Treeification / de-treeification events (if applicable)
	•	Prefer instrumentation around collision resolution paths.
Explicitly DISALLOWED:
	•	Only counting put() / get() calls
	•	Timing without collision metrics
Signal must approximate: "How much extra work did collisions force the map to do?"
6. Allocation / Memory Blowup
Applies to memory amplification attacks.
REQUIRED instrumentation depth:
	•	Instrument allocation hotspots:
	•	Object allocation counts
	•	Approximate allocated bytes
	•	Growth rate over execution
	•	Use counters at constructors or allocation-heavy loops.
Explicitly DISALLOWED:
	•	Heap usage snapshots only
	•	GC timing without allocation counts
Signal must approximate: "How fast and how large did memory consumption grow due to this input?"

7. Integer / Arithmetic Blowups (CWE-190 / CWE-681 → DoS via huge loops/allocations)

Applies to: size parsing, length fields, varints, base conversions, BigInteger/BigDecimal scale/precision, “count” headers.
Pathology: attacker-controlled numeric value drives loop bounds or allocation sizes.

REQUIRED instrumentation depth:
	•Instrument the exact loop or allocator call site where the number is consumed:
	•array growth methods (e.g., custom expand, ensureCapacity)
	•tight loops driven by parsed counts
	•constructors or factories that allocate based on parsed sizes
•Measure:
	•loop iterations executed in the hotspot
	•bytes allocated at that hotspot (or per-allocation totals if instrumented)

Explicitly DISALLOWED:
• Estimating “expected work” from the parsed integer value without measuring execution.
• Only timing the outer API.
Signal must approximate: “How much work/allocation was actually induced by numeric fields at the consumption hotspot?”

8. Algorithmic Complexity in Sorting / Comparison (CWE-407 / CWE-400)

Applies to: Collections.sort, TimSort, custom comparator-heavy pipelines, priority queues, ordering maps.
Pathology: comparator is expensive, comparator calls explode, or adversarial patterns trigger worst-case behavior.

REQUIRED instrumentation depth:
•Instrument:
	•comparator compare(a,b) method(s), OR
	•internal sort comparison hook points (when feasible in library code)
•Measure:
	•total comparator invocations
	•(optional) time spent inside comparator only (not whole request)

Explicitly DISALLOWED:
•Only measuring total sort time without isolating comparator cost.
•Counting “sort called N times”.

Signal must approximate: “How many comparisons (and/or comparator-cost) did sorting actually perform?”

[R45] Inputs That Reach the Mechanism (MANDATORY)
The Guidance's mutation operators MUST be able to produce, from its seeds and within the input size limit, inputs
of the shape and size the target's mechanism needs (`scale`, `input_bytes`). Byte flips and single-byte insertions
alone rarely build a deep, repeated or well-formed structure. Besides byte-level operators, every Guidance implements:
(a) Repetition: copy a chunk of the input (chosen at random or at a structure boundary) and repeat it k times in
    place, with k up to what fills the input size limit, including doubling a region or the whole input, so that a
    repeated structure (nesting, list items, labels, lines, whitespace, records) can reach the target's
    `input_bytes` in a few steps.
(b) A dictionary of tokens taken from the code on the target's attack path: the string and character literals the
    parser, matcher or decoder compares input against (keywords, delimiters, escape and meta characters, names of
    commands, macros, fields or tags, magic bytes), inserted or overwritten at random positions. Each token is a
    single syntactic unit found in the source; a dictionary MUST NOT contain an assembled triggering input ([R23]).
(c) Well-formed encoding for formats that reject random bytes: when the input is compressed, checksummed,
    length-prefixed or otherwise encoded (e.g. deflate, gzip, brotli, bzip2 or zstd streams, records with CRCs or
    length fields), the Guidance mutates a decoded representation (the plaintext, the records or fields) and encodes
    it with an encoder available on the test class path (the library's own encoder or one in the JDK), recomputing
    checksums and lengths, so that its inputs pass the format's checks and reach the sink. The encoder is part of
    the Guidance's mutation; the fuzz input model stays byte[]/InputStream ([R31]).
These operators are generic: they apply to whatever chunk, token or decoded content the search selects, never to a
fixed payload. Concrete triggering inputs (for example a string with the nesting depth that overflows the stack, or a
set of colliding keys) MUST NOT be written into the Guidance or its seeds ([R23]); the search must reach them.
[R46] Progress While the Signal Is Flat (MANDATORY)
A signal may stay at zero or constant until the input crosses a threshold (e.g. a buffer spills to a file above a
size; a decoder produces output only for a valid header). Retention MUST NOT keep only inputs with a non-zero or
improved signal when the seeds give zero: as a secondary criterion it keeps inputs that grow toward the target's
`input_bytes`, or that reach code on the attack path that was not reached before, so that the search can cross the
threshold. The Guidance must be able to generate an input as long as the target's `input_bytes` (at most the input
size limit) within its first minute of fuzzing; DoSGuide checks this (`input_growth`).
[R47] Measure Where the Resource Is Consumed (MANDATORY)
Retention signals measure the resource at the target's sink or in code the sink runs ([R30](B)). If no generated
input reaches that code, fix how the Guidance generates inputs ([R45], [R46]); do not move the measurement to code
that runs before the sink, and do not replace it with a property of the input such as its length ([R24]). A plan
revision that moves a target's retention signals from the sink to path hops before it is rejected.
